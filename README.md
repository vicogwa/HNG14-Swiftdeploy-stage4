# SwiftDeploy

A declarative deployment CLI that generates all infrastructure config from a single `manifest.yaml` and manages the full container lifecycle.

---


## Project Structure

```
swiftdeploy/
├── manifest.yaml                   # Single source of truth for all config
├── swiftdeploy                     # CLI entrypoint (Python 3)
├── app/
│   ├── main.py                     # Flask service (stable / canary modes)
│   ├── requirements.txt
│   └── Dockerfile                  # Multi-stage, non-root, <300 MB
├── templates/
│   ├── nginx.conf.j2               # Jinja2 template → nginx.conf
│   └── docker-compose.yml.j2      # Jinja2 template → docker-compose.yml
├── nginx.conf                      # Generated by `swiftdeploy init`
├── docker-compose.yml              # Generated by `swiftdeploy init`
└── README.md
```

## Quick Start

```bash
# 1. Build the Docker image
docker build -t swift-deploy-1-node:latest ./app

# 2. Generate config files from manifest
./swiftdeploy init

# 3. Run pre-flight checks
./swiftdeploy validate

# 4. Deploy the full stack
./swiftdeploy deploy

# 5. Verify it's running
curl http://localhost:8080/
curl http://localhost:8080/healthz
```

> **Windows users (Git Bash):** Run `export PYTHONUTF8=1` once before using the CLI to avoid Unicode errors in the terminal.

## manifest.yaml

The manifest is the single source of truth. All generated files are derived from it — never edit `nginx.conf` or `docker-compose.yml` directly.

```yaml
services:
  image: swift-deploy-1-node:latest
  port: 3000
  mode: stable
  version: "1.0.0"

nginx:
  image: nginx:latest
  port: 8080
  proxy_timeout: 30

network:
  name: swiftdeploy-net
  driver_type: bridge

logging:
  volume: swiftdeploy-logs
```

## CLI Subcommands

### `init`

Renders `nginx.conf` and `docker-compose.yml` from the Jinja2 templates using values in `manifest.yaml`.

```bash
./swiftdeploy init
```

Run this any time you change `manifest.yaml` and want to regenerate configs without redeploying.

---

### `validate`

Runs five pre-flight checks before deployment:

```bash
./swiftdeploy validate
```

| Check | What it verifies |
|---|---|
| manifest.yaml exists and is valid YAML | File is present and parseable |
| All required fields are present | No missing keys in manifest |
| Docker image exists locally | Image has been built |
| Nginx port is free | Port 8080 not already bound |
| nginx.conf is syntactically valid | Passes `nginx -t` inside Docker |

Exits with code `0` if all pass, `1` if any fail.

> Note: If the stack is already running, the port check will show `[FAIL]` for port 8080 — this is expected and not a problem.

---

### `deploy`

Runs `init`, brings up the full Docker Compose stack, and waits up to 60 seconds for the app healthcheck to pass.

```bash
./swiftdeploy deploy
```

What it does:
1. Regenerates `nginx.conf` and `docker-compose.yml` from templates
2. Runs `docker compose up -d`
3. Polls `http://localhost:8080/healthz` every 3 seconds
4. Reports healthy or exits with code `1` on timeout

---

### `promote`

Switches the application between `stable` and `canary` modes with a rolling restart — only the `app` container is recreated, nginx stays up.

```bash
./swiftdeploy promote canary
./swiftdeploy promote stable
```

What it does:
1. Updates `mode` in `manifest.yaml`
2. Regenerates `docker-compose.yml` with the new `MODE` env var
3. Recreates only the `app` container (`--no-deps --force-recreate`)
4. Confirms via `/healthz` and prints the response

In `canary` mode the app returns an `X-Mode: canary` response header and the `/chaos` endpoint becomes available.

---

### `teardown`

Stops and removes all containers, networks, and volumes.

```bash
./swiftdeploy teardown

# Also delete generated nginx.conf and docker-compose.yml
./swiftdeploy teardown --clean
```

## API Endpoints

| Endpoint | Method | Description |
|---|---|---|
| `/` | GET | Service info, current mode, version, timestamp |
| `/healthz` | GET | Health status and uptime |
| `/chaos` | POST | Inject chaos (canary mode only) |

### Chaos endpoint (canary mode only)

Simulate slow responses:
```bash
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "slow", "duration": 3}'
```

Simulate random errors:
```bash
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'
```

Recover to normal:
```bash
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
```

## Full Lifecycle Example

```bash
# Build
docker build -t swift-deploy-1-node:latest ./app

# Deploy
./swiftdeploy init
./swiftdeploy validate
./swiftdeploy deploy

# Verify
curl http://localhost:8080/
curl http://localhost:8080/healthz

# Promote to canary
./swiftdeploy promote canary
curl -i http://localhost:8080/healthz
# Look for X-Mode: canary in response headers

# Promote back to stable
./swiftdeploy promote stable

# View logs
docker logs swiftdeploy_nginx --tail 20

# Tear down
./swiftdeploy teardown --clean
```

## Design Decisions

**Single manifest as source of truth** — `nginx.conf` and `docker-compose.yml` are generated artefacts. This prevents config drift and makes the deployment fully reproducible from one file.

**Non-root container** — The app runs as `appuser` (UID 1000) with `cap_drop: ALL` and `no-new-privileges`, reducing the attack surface.

**Multi-stage Dockerfile** — Dependencies are installed in a builder stage and copied across, keeping the final image lean.

**Rolling promote** — Only the `app` container is restarted during a mode change. Nginx continues serving traffic with zero downtime.

**Python healthcheck** — Alpine's `busybox wget` has compatibility issues on some Docker Desktop versions. Using Python's built-in `urllib` for the healthcheck avoids this entirely.
