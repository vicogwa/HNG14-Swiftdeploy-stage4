# SwiftDeploy

A declarative deployment CLI that generates all infrastructure config from a single `manifest.yaml` and manages the full container lifecycle.

---

## Requirements

- Docker (with Compose v2 — `docker compose` not `docker-compose`)
- Python 3.10+
- pip

---

## Setup

### 1. Install Python dependencies

```bash
pip install pyyaml jinja2
```

### 2. Build the app image

```bash
docker build -t swift-deploy-1-node:latest ./app
```

> The image must be built before running `validate` or `deploy`.

---

## Usage

All commands run from the project root.

### `init`
Generates `nginx.conf` and `docker-compose.yml` from templates using `manifest.yaml` as the source of truth.

```bash
./swiftdeploy init
```

### `validate`
Runs 5 pre-flight checks and exits non-zero on any failure.

```bash
./swiftdeploy validate
```

Checks:
1. `manifest.yaml` exists and is valid YAML
2. All required fields are present and non-empty
3. The Docker image referenced in the manifest exists locally
4. The Nginx port is not already bound on the host
5. The generated `nginx.conf` is syntactically valid

### `deploy`
Runs `init`, brings up the full stack, and blocks until health checks pass (60s timeout).

```bash
./swiftdeploy deploy
```

### `promote`
Switches deployment mode between `stable` and `canary` with a rolling service restart.

```bash
./swiftdeploy promote canary
./swiftdeploy promote stable
```

What it does:
- Updates `mode` in `manifest.yaml` in-place
- Regenerates `docker-compose.yml` with the new `MODE` env var
- Restarts only the `app` container
- Confirms the new mode via `/healthz`

### `teardown`
Stops and removes all containers, networks, and volumes.

```bash
./swiftdeploy teardown

# Also delete generated config files
./swiftdeploy teardown --clean
```

---

## Endpoints

| Method | Path      | Description                                      |
|--------|-----------|--------------------------------------------------|
| GET    | `/`       | Welcome message with mode, version, timestamp    |
| GET    | `/healthz`| Liveness check with uptime in seconds            |
| POST   | `/chaos`  | Simulate degraded behaviour (canary mode only)   |

### Chaos payloads

```json
{ "mode": "slow", "duration": 3 }
{ "mode": "error", "rate": 0.5 }
{ "mode": "recover" }
```

---

## Canary mode

In canary mode, every response includes the `X-Mode: canary` header and the `/chaos` endpoint is active.

```bash
./swiftdeploy promote canary
curl -i http://localhost:8080/
# X-Mode: canary
```

---

## Nginx access log format

```
$time_iso8601 | $status | ${request_time}s | $upstream_addr | $request
```

View live:

```bash
docker exec swiftdeploy_nginx tail -f /var/log/nginx/access.log
```

## Project structure

```
swiftdeploy/
├── manifest.yaml          # Single source of truth — edit only this file
├── swiftdeploy            # CLI entrypoint
├── app/
│   ├── main.py            # Flask API service
│   ├── requirements.txt
│   └── Dockerfile
├── templates/
│   ├── nginx.conf.j2      # Nginx config template
│   └── docker-compose.yml.j2
├── nginx.conf             # Generated by init (do not edit)
├── docker-compose.yml     # Generated by init (do not edit)
└── README.md
```

## Full walkthrough

```bash
# 1. Install deps + build image
pip install pyyaml jinja2
docker build -t swift-deploy-1-node:latest ./app

# 2. Generate configs
./swiftdeploy init

# 3. Validate everything
./swiftdeploy validate

# 4. Deploy
./swiftdeploy deploy

# 5. Hit the service
curl http://localhost:8080/
curl http://localhost:8080/healthz

# 6. Promote to canary
./swiftdeploy promote canary
curl -i http://localhost:8080/healthz

# 7. Test chaos
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'

# 8. Recover and promote back to stable
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'

./swiftdeploy promote stable

# 9. Tear down
./swiftdeploy teardown --clean
```
